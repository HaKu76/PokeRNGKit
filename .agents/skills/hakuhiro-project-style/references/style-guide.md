# Hakuhiro 项目写作风格

## 依据与适用范围

本风格指南从以下公开或本地项目的 README、仓库描述、时间线和近期提交记录中提炼：

- `HaKu76/Haku76.github.io`
- `HaKu76/FF4TAY_Rare_Drop_Patch`
- `HaKu76/FF4TAY_Battle_FPS_Patch`
- `HaKu76/RS-TID-SID-Frame-Finder_H5`
- `HaKu76/PokeFinder_CHN` 等公开仓库的描述与发布状态

可以稳定复用的习惯包括：短句式仓库描述、结果优先的 README、以事实和验证为中心的技术说明、按日期或版本整理的进度条目，以及 `type: 中文动作短语` 形式的提交标题。

抽样仓库没有形成足够稳定的 GitHub Release 正文或构建元数据格式。因此，相关模板是对既有风格的推荐扩展，不是历史惯例。当前仓库的明确规范始终优先于本指南。

## 语气与措辞

- 默认使用简体中文，保持直接、克制、事实导向。
- 先写结果、用途或用户可观察到的变化，再补充实现细节。
- 使用“增加、修复、优化、更新、移除、验证、拒绝、保留”等明确动词。
- 保留命令、路径、文件名、版本号、地址、字节、哈希和技术名词的准确写法。
- 避免宣传口号、空泛形容词、未经验证的“完全兼容”“绝对安全”和无证据性能结论。
- 一段只承担一个主要信息任务；能用短段落或短列表表达时，不堆叠长句。
- 标题使用能直接说明内容的名词或动作，如“使用方法”“补丁原理”“构建与测试”“已验证版本”“已知限制”。

## 仓库描述

仓库 About 描述通常用一个短句交代平台或对象、产品/游戏和具体用途：

```text
<平台或对象> + <产品/游戏> + <具体用途>
```

已观察到的示例：

```text
Steam 版本最终幻想4：月之归还怪物稀有道具 100% 掉落补丁
Steam 版本最终幻想4：月之归还战斗帧数补丁
PokeFinder汉化
```

不要把 README 摘要、技术栈清单或营销口号塞进仓库描述。名称未定时，描述用途并明确“项目名称待定”，不要自行补一个品牌名。

## README 结构

优先采用以下阅读顺序，并按项目规模删去不适用的部分：

1. 标题和一句话结果：说明项目对哪个对象做什么。
2. 范围与安全边界：明确会改什么、不会改什么、何时拒绝操作。
3. 使用或安装：给出用户真正需要执行的最短步骤。
4. 原理或修改内容：用可核验的数据、偏移、协议或架构解释实现。
5. 构建与测试：列出真实可运行的命令和前置环境。
6. 已验证版本：记录精确文件、平台、架构、版本或校验信息。
7. 限制与恢复：说明不支持的情况、备份、回滚和数据丢失边界。
8. 署名与许可：记录来源、修改关系、许可证和必要免责声明。

状态尚未落地时直接写“尚无可用应用”或“计划”，不要把未来命令描述成当前能力。

## 进度与变更记录

发布变更或站点时间线按日期或版本分组，条目以动作词开头：

```text
- 新增：<用户可见能力或交付物>
- 优化：<体验、性能或结构变化>
- 修复：<问题与修复后的行为>
- 更新：<依赖、文档、数据或版本>
- 移除：<被删除内容与必要替代方案>
```

不要只写“若干优化”“修复问题”或文件列表。写清用户可观察结果或工程约束变化。

进度/交接文档不是发布日志。它至少应保持以下信息可恢复：

- 当前阶段、Git/发布状态和最近更新时间。
- 已确认决策、范围边界和未决问题。
- 已完成事项及其文件或验证证据。
- 第一个未完成动作，以及后续阶段的顺序。
- 已知警告、阻塞项和不能提前做的事项。
- 新环境恢复命令与最小交接上下文。

## 提交信息

近期稳定格式为：

```text
<type>: <中文动作短语>
```

高频且有历史依据的类型：

- `feat`：新增或改变用户可见能力。
- `fix`：修复错误行为。
- `style`：界面样式变化，不改变业务语义。
- `chore`：依赖、工具、维护或仓库事务。

需要时可沿用 Conventional Commits 的 `docs`、`test`、`refactor`、`build`、`ci` 等类型，但先服从目标仓库历史。这些类型是语义扩展，不应伪装成已观察到的高频习惯。

标题规则：

- 从实际 diff 概括一个主要变化，不按文件名罗列。
- 使用动作短语，不加句号，不写“完成了”“一些”“相关”等弱信息词。
- 只有破坏性变化确实存在时才使用 `!` 或 `BREAKING CHANGE`。
- 提交只包含文档时可用 `docs`；若目标仓库统一把文档维护归为 `chore`，服从其历史。
- 需要正文时说明原因、兼容/迁移影响和验证结果，不复述标题。

## 证据与验证措辞

使用能反映证据强度的标签：

```text
已通过：npm run format:check
已验证版本：1.2.3，Windows x64
当前限制：尚未验证离线升级
计划：在工程骨架完成后加入端到端测试
未运行：当前阶段尚无应用代码和构建配置
```

“命令存在”“配置声明支持”和“实际运行通过”是不同事实。版本表中的兼容范围也不等于浏览器或平台实测结果。

## 构建与发布信息

构建或发布记录应按实际情况包含：

- 版本、Git commit/tag、构建日期。
- 产物文件名、目标平台/架构、运行时要求、自包含状态和文件大小。
- 精确工具链版本、依赖锁文件和可复跑命令。
- 已执行测试、测试结果、已验证输入或环境。
- 每个公开产物的 SHA-256。
- 已知限制、升级/恢复方式、兼容性边界。
- 源码地址、上游署名、许可证和对应源码说明。

只列实际生成和验证的产物。没有 release 历史依据时，使用推荐模板并在项目第一次正式发布后根据真实反馈调整。

## 品牌与法律边界

- 正式名称未确认时写“工作名”或“名称待定”，不要设置中文暂名。
- 候选名称只放在明确的决策记录中，不写入 package、PWA、缓存键、法律文本或发布产物。
- 汉化、补丁、移植和衍生项目要明确上游关系，保留版权与许可证信息。
- 对商标或素材来源使用事实性说明，不暗示官方授权、合作或背书。
